---

Kete Loom is the skills library behind [Kete Code](https://ketecode.ai). It ships **skills** (folders the agent loads when relevant), **agents** (subagents it delegates to), **commands** (slash commands you type), **rules** (short always-on guidance), **hooks** (checks that run around the agent's tool calls and when it finishes) and **MCP server configs**. It takes a quality-first approach: fewer items, and every one of them is

- **portable**: uses the strictest common subset of the [Agent Skills](https://agentskills.io) format, so no host rejects it;
- **tested**: skills and agents ship trigger evals that check they load for the right requests and stay out of the way for the wrong ones, and the discipline skills add behaviour evals that check the agent actually follows them under pressure, compared with a run without the skill;
- **short**: under 300 lines, with detail moved into `references/` that the agent reads only when needed;
- **versioned and labelled**: semver, category and a risk level (`read-only`, `writes-files`, `runs-commands`, `network`) in its metadata;
- **script-backed** where the work is deterministic.

## Install

### Any agent (recommended)

```bash
npx @ketecode/loom install
```

This installs every skill into `~/.agents/skills` (read by Codex, OpenCode, Cursor, Gemini CLI, GitHub Copilot and Kete Code) and `~/.claude/skills` (Claude Code). Agents and commands go into `~/.claude/agents` and `~/.claude/commands` (read by Claude Code, and for agents also Cursor and VS Code Copilot), and into Codex, OpenCode, Gemini CLI, Kete Code and Kiro's own folders when those hosts are installed (Kiro also gets its own copy of the skills). Each agent and command is converted to the format its host expects. Restart your agent afterwards.

Or pick a profile instead of installing everything:

| Profile | What it installs |
|---|---|
| `minimal` | Test-first work, verification, security review, code review |
| `core` | The essentials, planning, git, onboarding and session handoff, **plus the language and framework packs your project uses** (detected from `package.json`, `go.mod`, `pyproject.toml`, `Cargo.toml`, `Dockerfile` and so on) |
| `developer` | `core` plus the four safety hooks |
| `strict` | `developer` plus the opt-in guardrails: read before edit, protected lint configs, background dev servers, staying in the worktree, no secret reads or planted instructions, warnings about injected text in what it reads, no accidental file truncation, a warning before the context fills up, valid commit messages, and no unfinished stubs or failing lint and type-check at the end |
| `method` | A full development method: design before code, granular plans, a fresh subagent per task with spec and quality review, systematic debugging, responding to review, worktrees and a clean finish |
| `project` | `method` plus project planning: a roadmap with phases in `.planning/`, requirement clarification, plan checks before code, acceptance testing with you, an idea backlog, feasibility spikes and recovery commands |
| `security` | Every security and compliance item, plus the safety hooks |
| `ai`, `data` | `core` plus every AI or data item |
| `business` | Marketing, LinkedIn content, research, investor, writing, PRD and operations skills |
| `design` | `core` plus UI work: design systems from product context with contrast-checked tokens and a DESIGN.md, polish, accessibility, motion, the UI auditor and `/design-ui` |
| `full` | Everything, with every hook that isn't opt-in |

```bash
npx @ketecode/loom install --profile developer     # run it inside your project so detection sees it
npx @ketecode/loom profiles                        # what each profile would install here
```

Profiles combine with `--skill`, `--agent`, `--command` and `--hook`, and `uninstall --profile <name>` removes only that profile's items.

Common options:

```bash
npx @ketecode/loom install --project                       # into this repo (.agents/ and .claude/), commit it for your team
npx @ketecode/loom install --skill tdd-workflow,security-review
npx @ketecode/loom install --agent code-reviewer --command verify
npx @ketecode/loom install --target claude                  # one host only
npx @ketecode/loom install --dir ~/.some-agent/skills       # any other agent
npx @ketecode/loom doctor                                   # what's installed, and which hosts can see it
npx @ketecode/loom uninstall                                # removes only items kete-loom installed
```

No Node? Use the shell installers, which fall back to a plain copy of the skills (agents and commands need the Node installer):

```bash
curl -fsSL https://raw.githubusercontent.com/Kete-org/kete-loom/main/install.sh | bash
```

```powershell
irm https://raw.githubusercontent.com/Kete-org/kete-loom/main/install.ps1 | iex
```

| Host | Command |

| Codex | `codex plugin marketplace add Kete-org/kete-loom` then `codex plugin add kete-loom@kete-loom` |

| Any skills CLI | `npx skills add Kete-org/kete-loom` |

Plugin installs update through the host's own plugin manager. Use either a plugin install or the `npx` installer for a given host, not both, or the host may list each skill twice.

## A development method

Install `--profile method` for a complete way of working, from idea to merged branch, with a review gate at each step:

| Step | Use | What happens |
|---|---|---|
| 1. Design | `/brainstorm` (`design-brainstorming`) | One question at a time, two or three approaches with trade-offs, your approval section by section, HTML mockups for visual choices, then a design doc in the repo. |
| 2. Isolate | `git-worktrees` | A separate, git-ignored worktree with dependencies installed and a baseline test run, so existing failures are known. |
| 3. Plan | `/plan-feature` (`implementation-plans`) | Tasks of a few minutes each, with exact files, the failing test to write first, the command to run and its expected output, and a commit per task. |
| 4. Build | `subagent-driven-development` with the `task-implementer` agent | A fresh subagent per task works test-first and reports a status. The `spec-reviewer` checks it against the task, then `code-reviewer` checks its quality, looping until both pass. |
| 5. Debug | `/debug` (`systematic-debugging`) | Root cause before any fix: reproduce, trace the bad value to its source, one hypothesis at a time. After three failed fixes it stops and questions the design. |
| 6. Review | `responding-to-code-review` | Checks each comment against the code, pushes back with evidence when a suggestion is wrong, and replies in the review thread. |
| 7. Finish | `/finish-branch` (`finishing-a-branch`) | Tests first, then merge locally, open a pull request, keep the branch, or discard it (only after you type a confirmation). |

`/feature-dev` runs the whole sequence with a stop for your approval between stages, and the `use-skills` rule keeps the agent reaching for these skills instead of working from memory.

For work bigger than one feature, `--profile project` adds the planning around it. Everything is kept in plain Markdown files under `.planning/`, which you can read, edit and commit:

| Need | Use |
|---|---|
| A roadmap of milestones and phases tied to numbered requirements, with current state that survives across sessions | `project-roadmap`; `/progress` says where things stand and names the next action |
| Requirements pinned down before planning: gray areas, the agent's assumptions with evidence, the edge cases | `spec-clarification`, `assumptions-analyzer` |
| A plan checked against its goal before any code is written | `plan-checker` |
| "Can this even work?" answered with a timeboxed experiment and a verdict | `feasibility-spike` |
| Acceptance testing with you, one deliverable at a time | `/uat` (`acceptance-testing`), `ui-auditor` |
| Ideas and todos saved without derailing the current task | `/capture` (`idea-backlog`) |
| Recovery: fix a list of review findings, find out why a multi-session effort went wrong, safely undo work | `/fix-findings`, `/forensics`, `/revert-work` |

### Learning from every session

Skills get better from friction found in real work, so Kete Loom keeps a log of it. The `skill-observations` skill notes each finding as it happens: a correction you gave, a rule the agent broke, a missing step, or a workflow worth its own skill. It writes each one as a small file through `kete-loom observe`. `/skill-review` later turns the log into changes you approve one by one.

```bash
npx @ketecode/loom observe scan        # open findings, whether a review is due, rules broken twice
npx @ketecode/loom observe list --skill tdd-workflow
```

The log is yours and stays on your machine, in `~/.kete-loom/observations/`. It is kept at user scope, so findings aren't split across projects or lost with a deleted worktree. The CLI enforces the bookkeeping:
- ids never repeat, and an existing file is never overwritten;
- a restated finding is refused in favour of extending the original;
- every finding must record which related skills were checked;
- a rule broken twice is flagged for a hook (`/hookify`) rather than another rewording.

Reviews stage changes and never edit an installed Kete Loom skill in place, since `update` would overwrite it; those become a draft upstream change plus, if needed, a project rule. With the `load-session-context` hook installed, each session starts knowing what is open. Both items are in `--profile method`.

The approach is adapted from [Task Observer](https://github.com/rebelytics/one-skill-to-rule-them-all) by Eoghan Henn and contributors (CC BY 4.0).

## Hooks

Checks that run automatically at points in the agent loop: before a shell command or a file edit (and can block it, with a reason the agent sees), after an edit, after a file or web read or any tool call (and can add a note for the agent), when a session starts, or when the agent finishes its turn (and can send it back to work). Hooks are opt-in: `install` never adds them unless you ask. Hooks marked opt-in change how the agent works, so `--hooks` leaves them out; name them, or use `--profile strict`.

```bash
npx @ketecode/loom install --hook block-dangerous-commands,guard-secrets   # chosen hooks
npx @ketecode/loom install --hooks                           # everything, plus every hook not marked opt-in
npx @ketecode/loom uninstall --hook block-dangerous-commands
```

The installer registers each hook with Claude Code and every other host it finds: Claude Code and Gemini CLI in their `settings.json`, Kete Code in `kete.json`, Codex and Cursor in their `hooks.json`, Copilot CLI in `~/.copilot/hooks/` and OpenCode as a plugin. It only adds and removes its own entries, backs a file up to `<file>.kete-loom-backup` before changing it, and never rewrites a file that has comments (it prints the snippet to paste instead). Codex runs a new hook only after you trust it with `/hooks`. Hooks install for your user only, not per project. Cursor has no hook before an edit and OpenCode none that adds context at session start, so those hooks skip them; hooks that send the agent back when it finishes skip Kete Code and OpenCode, whose stop hooks can't. Kiro hooks belong to its agent configs and aren't installed.

## MCP servers

Curated MCP server configs, registered with every host you use in that host's own format. None of them puts a token in a config file: remote servers sign in with OAuth through the host (`/mcp` in Claude Code, `codex mcp login`, `kete mcp auth`…), and local servers need no secrets. MCP servers are opt-in: `install` never adds them unless you name them.

```bash
npx @ketecode/loom install --mcp github,playwright          # chosen servers
npx @ketecode/loom install --profile mcp-web                # a pack: playwright, chrome-devtools, context7, fetch, exa, firecrawl
npx @ketecode/loom uninstall --mcp github
```

Packs: `mcp-web`, `mcp-code` (GitHub, Git, Sentry, and `lsp` for language-server navigation), `mcp-team` (Linear, Notion, Atlassian), `mcp-cloud` (Cloudflare, Vercel, Supabase read-only, Stripe), `mcp-design` (Figma). Claude Code servers are added with `claude mcp add-json --scope user` (or `.mcp.json` with `--project`); Codex gets them in a marked block of `config.toml`; Gemini CLI, Cursor, Copilot CLI, OpenCode and Kete Code in their MCP config files. A server you already configured under the same name is never replaced. On Windows, Claude Code servers can only be added this way with Claude Code's native installer (`claude.exe`); with an npm install, kete-loom prints the `claude mcp add-json` command to run yourself. Copilot CLI gets local servers only, because it has no documented way to sign in to remote ones.

## Housekeeping

```bash
npx @ketecode/loom@latest update      # refresh exactly what you installed, in the hosts it's in
npx @ketecode/loom outdated           # installed items older than the latest Kete Loom
npx @ketecode/loom audit              # score this project's readiness for coding agents, with fixes
npx @ketecode/loom check ./my-skills  # lint your own skills, agents, commands, rules or hooks
npx @ketecode/loom doctor             # what is installed where
npx @ketecode/loom doctor --fix       # repair the hook runtime and drop stale hook registrations
```

`audit` checks the things that make agents work well in a repository: agent instructions (`AGENTS.md`/`CLAUDE.md`), the Kete Loom packs for the stack it detects, test and lint commands, CI, the safety hooks, and that `.env` files are ignored and not committed. It exits non-zero when a check fails, so it can run in CI.

Inside your agent, `/loom` finds the right items for a task, `/checkpoint` saves a restorable snapshot without committing, `/sessions` lists and tidies handoff notes, `/codemap` writes a short architecture map, `/model-route` suggests a model tier, and `/aside` answers a side question without derailing the task. For your agent setup itself, `/lint-agent-config` checks AGENTS.md, skills, hooks, MCP configs and plugin manifests for broken or risky settings, `/rules-review` compares your recent sessions with your rules and suggests what to add, reword or retire, and `/usage-report` summarises token use and cost from local session logs.

## Contributing

Read [`docs/SKILL_SPEC.md`](docs/SKILL_SPEC.md) (skills, agents and commands) and [`CONTRIBUTING.md`](CONTRIBUTING.md). Every pull request must pass:

```bash
npm run lint      # frontmatter, length, references, evals, manifest versions
npm test          # installer and linter tests
npm run eval      # trigger and behaviour eval file checks (CI also runs them live)
```

Two kinds of evals keep items honest:

- **Trigger evals** (`evals/triggers.json`): a model routes realistic prompts and near misses the way hosts do, and each item must be picked for its own prompts and only those.
- **Behaviour evals** (`evals/behavior.json`): scenarios that pressure the agent to skip the item's discipline ("just patch it, we ship in ten minutes"). Each runs with the item and without it, a judge model grades every reply, and the report shows what the item adds. `--host claude` runs them as real headless Claude Code sessions.

```bash
npm run eval:live -- --skill my-skill                     # routing
npm run eval:behavior -- --live --skill my-skill          # behaviour, with and without the skill
```

The `skill-authoring` skill walks your agent through writing a new skill to this standard.
