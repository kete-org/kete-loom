# LLM evals

An eval is a test suite for behaviour that isn't deterministic. It turns "seems better" into a number you can compare across prompt versions and models. This skill builds the suite. To grade one agent's existing outputs and report failure patterns, delegate to the `agent-evaluator` agent. To rewrite the prompt itself, use `prompt-engineering`.

## 0. Define what you measure

1. State the feature's job in one sentence and list 2 to 5 **criteria** that decide a good output (for example: correct label, cites a source, under 120 words, refuses out-of-scope requests).
2. For each criterion, decide if it can be checked by code. Prefer code. Use a model grader only where code can't decide.
3. Agree a ship bar with the user (for example "≥ 95% on correctness, 0 safety failures"). If the user can't give one, **stop and ask**; a suite with no bar can't block a release.
4. Search the codebase for an existing eval harness, test runner or dataset folder before creating a new one.

## 1. Build the case set

- **Sources, in order of value:** real production inputs (from logs, redacted), reported bugs and user complaints, hand-written edge cases, synthetic cases generated by a model and then reviewed by a person.
- **Coverage:** typical inputs, hard inputs, edge cases (empty, very long, wrong language, ambiguous), adversarial inputs (prompt injection, requests the feature must refuse), and one case per past bug.
- **Size:** 20 to 50 good cases beat 1,000 unreviewed ones. Grow it as failures appear.
- Each case is a record with an id, the input, the expected output or the facts a good answer must contain, tags (category, difficulty, source), and the date added. Store it in the repo as JSONL or similar, under version control.
- Never put real personal data or secrets in the case set; redact first. If unsure whether data may be used, **stop and ask the user**.

## 2. Avoid leakage

- Split the set: a **dev** portion you look at while editing prompts, and a **held-out** portion you only run to report results. Never copy held-out inputs into prompts as few-shot examples.
- When you add a production failure, put it in dev first; move a fresh sample into held-out periodically.
- Don't evaluate a model on cases it may have trained on (public benchmarks, text copied from the web) and call it generalisation.
- When a model generates synthetic cases, don't use the same prompt you are evaluating to create them.

## 3. Choose graders

Use the cheapest grader that decides the criterion correctly.

| Grader | Use for | Notes |
|---|---|---|
| Exact / normalised match | labels, IDs, numbers, yes/no | Normalise case, whitespace and number format first |
| Code check | JSON validity, schema, length, required keywords, regex, citation present, tool called with right args | Deterministic, fast, run on every case |
| Reference similarity | short factual answers | Only as a hint; similar text can be wrong |
| Rubric, model-graded | tone, helpfulness, faithfulness to a source, reasoning quality | Needs calibration (section 4) |
| Pairwise, model-graded | "is B better than A?" between two prompt versions | Randomise order to cancel position bias |
| Human review | ship decisions on subjective quality, safety, legal or medical content, calibrating judges | Slow; sample, don't review everything |

Grader templates and a judge prompt are in `references/graders.md`. Read it before writing a model-graded rubric.

## 4. Make model graders trustworthy

1. Grade one criterion per judge call, with a short rubric that defines each score level in concrete terms. Prefer pass/fail or a 1 to 3 scale over 1 to 10.
2. Ask the judge for its reasoning first, then the verdict in a fixed field your code parses.
3. Use a capable model as judge, and preferably not the exact model and prompt under test.
4. **Calibrate:** have a person label 20 to 50 outputs, run the judge on them, and measure agreement. Fix the rubric until agreement is acceptable to the user; report the agreement rate alongside every judged score.
5. Re-calibrate when you change the judge model or rubric.

## 5. Run and track

1. Run every case with the exact production config: model version, prompt version, temperature, tools.
2. Outputs vary between runs. Run each case several times (3 or more when results are close) and report the pass rate per case, not just the mean.
3. Store each run as a record: date, git commit, prompt version, model, per-case results, aggregate scores, cost and latency.
4. Compare against the last accepted run **case by case**. A higher average that breaks previously passing cases is a regression to report, not a win.
5. Wire the fast, code-graded portion into CI so prompt or model changes can't merge when it drops below the bar. Run expensive judge-graded suites on demand or nightly.

## 6. When to involve people

Bring in human review when:
- Setting or changing the ship bar.
- Calibrating a judge model (section 4).
- The domain is high-stakes (health, finance, legal, safety) or the output reaches users unreviewed.
- Judge scores and user feedback disagree.
- Labelling new production failures before they join the case set.

Give reviewers the rubric, blind them to which version produced the output, and record their labels in the case set.

## Never

- Never report a score without the case count, run count and grader type.
- Never tune a prompt on the held-out set.
- Never treat a judge model's score as ground truth before checking it against human labels.
- Never delete a failing case to raise the score. Fix the feature or mark the case as wrong, with a reason, after the user agrees.

## Report back

```
Feature: <name>   Prompt: <version>   Model: <exact id>
Cases: <n dev> dev / <n held-out> held-out   Runs per case: <k>
Criterion          Grader        Score     Bar     Δ vs last
<correctness>      exact         47/50     ≥ 45    +2
<faithfulness>     judge (κ=..)  44/50     ≥ 45    -1  ← regression
Newly failing: <case ids>   Newly passing: <case ids>
Verdict: ship | don't ship, because <one line>
```
