# Next.js App Router patterns

Keep data and secrets on the server, ship the least client JavaScript, and be explicit about what is cached. General component rules live in `react-patterns`; render speed in `react-performance`.

## 0. Before you change anything

1. Read `next` in `package.json`. Behaviour differs a lot between majors:
   - 15: `params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` became async (sync access still worked with warnings). `fetch` and `GET` Route Handlers stopped being cached by default.
   - 16: sync access to those APIs is removed; `middleware.ts` is deprecated in favour of `proxy.ts`; `revalidateTag` takes a second `cacheLife` argument; Turbopack is the default bundler; `next lint` is removed; Node.js 20.9+ is required.
2. Check `next.config.*` for `cacheComponents: true`. It switches the app to a different caching model (`"use cache"`, no `dynamic`/`revalidate`/`fetchCache` segment config); see `references/caching.md` for both models. Write new code in the model the app uses.
3. Confirm the project uses `app/`. If it uses `pages/`, stop and tell the user this skill covers the App Router.
4. If the repo ships version-matched docs (an `AGENTS.md` pointing into `node_modules/next/dist/docs/`), read those before guessing.

## 1. Server vs Client Components

Everything in `app/` is a Server Component unless its module (or an importer) starts with `"use client"`.

Make a component a Client Component only if it needs one of: state or effects, event handlers, browser APIs, or a library that uses them. Then:

1. Push `"use client"` to the **leaves**: a `LikeButton`, not the whole page.
2. Pass Server Components into Client Components as `children` or props rather than importing them inside the client file.
3. Props crossing the boundary must be serialisable: plain objects, arrays, strings, numbers, Dates, Promises, Server Actions. No class instances, functions (other than Server Actions) or symbols.
4. Pass only the fields the client needs, never whole DB rows or user records. Everything you pass is visible in the page payload.
5. Mark server-only modules (DB, secrets, SDKs with keys) with `import "server-only"` so a client import fails the build.
6. Context providers are Client Components; render them as deep as possible and wrap `{children}`.

`"use server"` marks Server Actions (functions callable from the client). It is not the opposite of `"use client"` and is never needed to make a Server Component.

## 2. Request APIs and params

```tsx
export default async function Page(props: PageProps<"/blog/[slug]">) {
  const { slug } = await props.params;
  const { q } = await props.searchParams;
  const theme = (await cookies()).get("theme")?.value;
  // ...
}
```

- `PageProps`, `LayoutProps` and `RouteContext` helpers are generated by `next typegen` (15.5+) or during `next dev`/`next build`.
- In a Client Component, unwrap a passed `params` promise with React `use()`, or use `useParams()`/`useSearchParams()`.
- `useSearchParams()` in a client component needs a `<Suspense>` boundary above it, or the build may fail or bail out of static rendering.
- Treat `params` and `searchParams` as untrusted input; validate them (for example with zod) before using them in queries.

## 3. Data fetching and caching

1. Fetch in Server Components, close to where the data is used. Use `React.cache()` to dedupe a non-`fetch` call (ORM, SDK) within one request; identical `fetch` calls are memoised automatically.
2. Start independent requests together (`Promise.all`) or in sibling components behind separate `<Suspense>` boundaries. Avoid sequential `await`s in a layout.
3. Wrap slow or request-specific parts in `<Suspense fallback>` (or add `loading.tsx`) so the rest streams.
4. Choose caching on purpose, per data source: how stale may it be, and what event invalidates it? Then apply the matching model from `references/caching.md`.
5. After a mutation, invalidate what changed: `revalidatePath`, `revalidateTag(tag, profile)` (16) or `updateTag(tag)` for read-your-writes inside a Server Action (16).
6. Development never caches pages. Always confirm caching behaviour with `next build && next start`.

## 4. Route Handlers (`app/**/route.ts`)

- Export named functions per method: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`. Use the Web `Request`/`Response` (or `NextRequest`/`NextResponse`).
- A `route.ts` cannot sit in the same segment as a `page.tsx`.
- Use them for webhooks, public APIs consumed by other clients, file downloads and OAuth callbacks. For mutations from your own UI, prefer Server Actions.
- Webhooks: read the raw body with `await request.text()` before verifying a signature; don't `request.json()` first.
- Authenticate and authorise inside every handler; nothing upstream does it for you.

## 5. Server Actions

```ts
"use server";
import { z } from "zod";
import { revalidatePath } from "next/cache";

const Input = z.object({ title: z.string().min(1).max(200) });

export async function createPost(prev: State, formData: FormData): Promise<State> {
  const session = await auth();                       // 1. authenticate
  if (!session) return { error: "Sign in first" };
  const parsed = Input.safeParse({ title: formData.get("title") }); // 2. validate
  if (!parsed.success) return { error: "Invalid title" };
  await db.post.create({ data: { ...parsed.data, authorId: session.user.id } }); // 3. authorise by owner
  revalidatePath("/posts");                           // 4. invalidate
  return { ok: true };                                // 5. return only what the UI needs
}
```

- Every exported action is a public POST endpoint. A page-level auth check does **not** protect the actions on that page. Check auth and resource ownership inside each action (or in a `server-only` data access layer it calls).
- Validate every argument; types are not runtime checks.
- Return small plain objects; never return raw DB records.
- `redirect()` throws to work: call it outside `try/catch`, or rethrow.
- Use with `useActionState` for errors and pending state, `useOptimistic` for instant feedback.
- Actions are rejected when the `Origin` host differs from the app host (`x-forwarded-host` or `host`). If a reverse proxy doesn't forward the public host, or the app is served from extra domains, list them in `experimental.serverActions.allowedOrigins`; when self-hosting several instances, set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` so all instances share the key.

## 6. Metadata

- Export `metadata` (static) or `generateMetadata` (dynamic) from `layout.tsx`/`page.tsx`. Only in Server Components.
- Set `metadataBase` in the root layout so relative Open Graph URLs resolve.
- Use `title.template` in the root layout (`"%s | Site"`) and plain `title` in pages.
- File conventions: `opengraph-image.tsx`, `icon.tsx`, `sitemap.ts`, `robots.ts`. In 16 their `params` (and image `id`) are promises.
- `generateMetadata` and the page share fetches through memoisation or `React.cache()`; don't fetch twice deliberately.
- Viewport and theme colour go in `viewport`/`generateViewport`, not `metadata`.

## 7. Middleware / proxy

- 15: `middleware.ts` at the root (or `src/`), exporting `middleware` and `config.matcher`.
- 16: rename to `proxy.ts` exporting `proxy`; it runs on the Node.js runtime only. If you need the Edge runtime, keep `middleware.ts` and tell the user. Don't blindly rename.
- Keep it cheap: redirects, rewrites, header and cookie tweaks, optimistic auth redirects.
- Never rely on it as the only authorisation check; re-check in pages, Route Handlers and Server Actions.
- Always set a `matcher` that excludes `_next/static`, `_next/image` and static files.

## 8. Environment variables

- Only variables prefixed `NEXT_PUBLIC_` reach the browser, and they are **inlined at build time**. Changing them needs a rebuild; a Docker image built once can't pick up new public values at run time.
- Never prefix a secret with `NEXT_PUBLIC_`. Read secrets only in server-only modules.
- Load order: `.env.$(NODE_ENV).local`, `.env.local` (skipped when `NODE_ENV=test`), `.env.$(NODE_ENV)`, `.env`. Commit only non-secret defaults.
- To read a server variable at request time rather than at build, make the code dynamic (`await connection()` from `next/server` first, 15+).
- Validate required variables at startup (a small zod schema in `env.ts`) so a missing one fails loudly.

## 9. Deployment pitfalls

- Run `next build` locally before shipping; many errors (missing `Suspense` around `useSearchParams`, invalid segment config, missing `default.tsx` for parallel routes in 16) only appear there.
- Self-hosting: use `output: "standalone"` for Docker and copy `public/` and `.next/static` into the image. With several instances, configure a shared cache handler or ISR results diverge per instance.
- Images: configure `images.remotePatterns` (not the deprecated `domains`). In 16, `images.qualities` defaults to `[75]`.
- Edge runtime has no Node APIs (`fs`, most DB drivers); keep DB access on the Node runtime.
- Long work in a Server Action or Route Handler hits the host's function timeout; move it to a queue or background job.

## Never

- Never put `"use client"` on a layout or page just to make one hook work.
- Never import a server-only module from a client file, or read `process.env.SECRET` in one.
- Never trust that middleware/proxy or a hidden button protects a Server Action.
- Never use the single-argument `revalidateTag(tag)` on 16, or `"use cache"` without `cacheComponents` enabled.

## Stop and ask the user

- Before enabling `cacheComponents`, the React Compiler or a major-version upgrade; each changes behaviour app-wide.
- Before changing the runtime (`edge` vs `nodejs`) or the deployment output mode.
- When it's unclear how fresh a piece of data must be.

## Report back

End with: routes and files changed, which components are client and why, the caching decision for each data source (cached for how long, invalidated by what), the `next build` result, and anything not verified in a production build.
