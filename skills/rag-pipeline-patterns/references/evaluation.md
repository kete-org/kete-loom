# Evaluating a RAG pipeline

Read this when building the eval set or computing metrics.

## Building the eval set

1. Collect 20 to 50 real questions to start (support tickets, search logs, chat logs). Grow to a few hundred over time.
2. For each, record the ids of the documents (or chunks) that answer it, and a short reference answer. A subject-matter expert should confirm these.
3. Add 10 to 20 percent unanswerable questions (the corpus doesn't cover them) with an empty relevant set.
4. Add hard cases: exact identifiers (error codes, SKUs), follow-up questions that need history, questions whose answer changed recently, questions where the user lacks access to the answering document.
5. Freeze the set in version control as JSONL: `{"id": "q17", "question": "...", "relevant": ["doc_42"], "answer": "..."}`. Never tune on the test portion; keep a held-out split if you iterate a lot.

Synthetic questions generated by a model from your chunks are fine for extra coverage, but they over-reward chunk-shaped questions. Never use only synthetic data.

## Retrieval metrics

For each question, take the ranked list of retrieved ids (deduplicated to doc level if relevance is labelled per document).

- **recall@k** = |relevant ∩ top-k| / |relevant|. Average over answerable questions.
- **hit@k** = 1 if any relevant id is in top-k, else 0. Useful when one document is enough.
- **MRR** = mean of 1 / (rank of first relevant id), 0 if none in the list.
- **nDCG@k** = DCG@k / ideal DCG@k, with DCG = sum over positions i of rel_i / log2(i + 1). Use graded relevance if you have it.

Measure at the retriever's k (before rerank) and at the final k sent to the prompt. The gap shows what reranking and trimming cost.

## Generation metrics

- **Faithfulness**: split the answer into claims; the fraction supported by the provided sources. Usually judged by a model with a fixed rubric; spot-check the judge against human labels on 30+ examples before trusting it.
- **Answer correctness**: compare to the reference answer (model judge or human).
- **Citation accuracy**: fraction of citations that point to a sent chunk that actually supports the sentence.
- **Refusal on unanswerable**: fraction of unanswerable questions where the system said it didn't know.

## Running it

- Run the full set on every pipeline change and log: git commit, settings (chunk size, model, k values, prompt version), and every metric.
- Report before and after side by side, and list questions that flipped from pass to fail. Regressions on individual questions matter more than a small average gain.
- Judges and generators are non-deterministic: fix temperature at 0 where possible and repeat runs if differences are small.
